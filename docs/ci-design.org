* 2. The workflow: `.github/workflows/check.yml`

** 2.1 Job: `check-go`

Steps, in the order the Makefile's own `check` target runs them
(`check: fmt-check lint vet vuln test cov` in =go/Makefile=):

| Step | Why it exists |
|------+----------------|
| Checkout | full checkout (not sparse) — needed because the module is at =go/go.mod=, and =make lint=/=make vuln= walk the whole =go/= tree |
| Set up Go | pins the Go toolchain to =go/go.mod='s `go 1.26.5` via `go-version-file`, so CI and local `go-version path` can never silently drift apart |
| Install check tools | `golangci-lint` and `govulncheck` are not vendored or in the module's own dependency graph — the Makefile's own comments call this out (`lint` silently falls back to `go vet` and returns 0 if golangci-lint is missing; `vuln` hard-fails if `govulncheck` is missing). Installing explicitly and asserting presence prevents `lint` from passing green while checking nothing |
| Assert tools present | belt-and-braces on the row above — fails loudly rather than silently degrading |
| Format check | `make fmt-check` — gofmt drift gate |
| Lint | `make lint` — golangci-lint over `./...` |
| Vet | `make vet` — `go vet ./...` |
| Vuln (blocking) | `make vuln` — govulncheck, hard fail on any finding |
| Test | `make test` — `go test ./...` |
| Coverage | `make cov` — per-package coverage table (informational; not yet gated on a threshold, matching the exemplar, which also does not gate on a number) |

Each Makefile target is invoked as its own step (rather than one
`make check` step) purely so a failure is attributable at a glance in the
Actions UI — this mirrors voicelab' own choice to split rather than
collapse, not a re-derivation.

** 2.2 Security posture — checked line by line against the house rules

| Requirement | How this workflow satisfies it |
|-------------+----------------------------------|
| Every `uses:` pinned to a full 40-char commit SHA | both actions (`checkout`, `setup-go`) are pinned to SHAs, `# vX.Y.Z` trailing comments only |
| `permissions: {}` default at workflow top | yes; `check-go` opts in to `contents: read` only |
| Never `secrets: inherit` | no `secrets:` key appears anywhere in the file; the job needs none |
| Never `pull_request_target` | trigger is `pull_request` |
| Two-job build/scan separation if a scan job is added | not applicable yet — no container image is built by this repo; noted for when/if one is |

* 3. Dart job — exact shape (ADDED 2026-08-07)

** 3.1 Why this section was stale, and what that cost

The original text of this section — retained below the line for the record —
argued correctly that a Dart job must not be added against an empty tree,
because "a green no-op job reads as 'Dart is covered' when it covers nothing."

Its premise then expired without the conclusion being revisited. Tranche 0
landed =ui/pkg/desktop_kit= (219 tracked =.dart= files, 98 test files, 1818
test cases) and =ui/Makefile= with a real `check: fmt-check analyze test`
target — on this same branch. From that commit forward the reasoning inverted:
the no-op risk was gone, and the live risk was a workflow that ran only
=check-go=.

Nothing failed, which is the point. =check-go= passed, and had this branch been
fast-forwarded onto =main=, =main= would have gone green while never invoking
=flutter analyze= or =flutter test= on 219 files. The gate does not have to be
broken to stop being a gate; its *premise* only has to go stale. =ui/Makefile='s
own header records the same false-green from the Makefile side, which means it
was observed once and the CI half was still missed.

Added ahead of landing, since `on: push: branches: [main]` makes landing the
moment the claim starts being made.

** 3.2 Three corrections applied to the draft below

The drafted body was reused rather than redesigned, with three changes:

1. *SHA pin resolved fresh.* The draft left
   =subosito/flutter-action@<PIN-TO-SHA-AT-THAT-TIME>=. Resolved to
   =1c5eb12d812966ca84680edc38353a0851c8fd56= (v2.14.0).
   TRAP: v2.14.0 is an ANNOTATED tag, so `git ls-remote <url> refs/tags/v2.14.0`
   returns =7814e4f6…= — the *tag object*, which Actions cannot resolve. The
   commit is the `^{}` dereferenced line. Both are 40 hex chars, so a
   "is it SHA-pinned?" check passes either way and only the wrong one fails at
   run time.
2. *A `make get` step was missing.* The draft went straight from `fmt-check` to
   `analyze`. =ui/Makefile= deliberately keeps `get` out of `check`, and
   `flutter analyze` needs resolved dependencies — so analyze would have failed
   for a reason unrelated to the code.
3. *Toolchain passed explicitly.* =ui/Makefile= defaults
   =FLUTTER ?= $HOME/flutter/bin/flutter= (Flutter is not on PATH in
   these workspaces). That path does not exist on a runner, so the job sets
   =FLUTTER: flutter= / =DART: dart= in `env:` rather than editing the Makefile
   — the `?=` exists for this, and hardcoding a runner path would break local
   use in exchange.

Added beyond the draft: an *"Assert the gate covers at least one package"*
step, mirroring =check-go='s "Assert tools present". =ui/Makefile= drives every
target with `for p in $(PACKAGES)` over a `pkg/*/pubspec.yaml` wildcard; if
that glob matches nothing, every target iterates an empty list and exits 0.
That is the same false-green in a third costume, so it is asserted rather than
assumed.

** 3.3 The job as drafted (historical — see 3.2 for what changed)

Original rationale, preserved: when Dart code and its Makefile land in =ui/=,
add this job as a peer of `check-go` (the workflow is already structured for
it — see the header comment in =check.yml=):

#+begin_src yaml
  check-ui:
    name: Dart (ui/)
    runs-on: ubuntu-latest
    permissions:
      contents: read
    defaults:
      run:
        working-directory: ui
    steps:
      - name: Checkout
        uses: actions/checkout@df4cb1c069e1874edd31b4311f1884172cec0e10 # v6.0.3

      - name: Set up Flutter
        uses: subosito/flutter-action@<PIN-TO-SHA-AT-THAT-TIME> # vX.Y.Z
        with:
          channel: stable
          # or flutter-version-file: ui/pubspec.yaml if the constraint is
          # narrow enough to resolve one version from it

      - name: Format check
        run: make fmt-check

      - name: Analyze
        run: make analyze

      - name: Test
        run: make test
#+end_src

Notes for whoever adds it:
- Do NOT reuse =voicelab/release.yml='s =subosito/flutter-action@v2= pin
  verbatim — that pin is itself a finding (§5): it is tag-pinned, not
  SHA-pinned. Resolve a fresh SHA for whatever Flutter action version is
  current at that time, per the house rule (verify a new digest/SHA
  before pinning, don't copy a stale or already-flagged one).
- Keep `check-go` and `check-ui` as separate jobs (not steps in one job)
  so they run in parallel and a Go-only change does not wait on Dart
  tooling installation, and vice versa.
