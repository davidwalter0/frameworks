* Scope and method

This answers the README's request to "list the projects using flutter under
=~/go/src/github.com/davidwalter0/=" and to characterise them in *two separate
tables* — high-level function, and supporting widgets.

Method, so the numbers are reproducible:

#+begin_src sh :results verbatim
# application count
find ~/go/src/github.com/davidwalter0 -name pubspec.yaml -not -path '*/.dart_tool/*'
# dart file count per app
find <app>/lib -name '*.dart' | wc -l
# kit adoption
grep -rl "package:desktop_kit/" <app>/lib | wc -l
# kit pin
grep -A2 'desktop_kit:' <app>/pubspec.yaml
#+end_src

"Kit files" counts files under =lib/= containing at least one
=package:desktop_kit/= import — a file-level adoption measure, not a
call-site one. It understates depth (one import may drive a whole pane) and
overstates breadth (a single =DeskTheme= import counts the same as a full
editor embed), so read it as a *ratio trend* across migration, not an
absolute.

Three facts to carry forward:

1. *The pin surface is fragmented*: two apps on =path=, one on a bare sha, six
   on =v0.2.3=, one on =v0.2.4=, one on nothing. A big-bang move breaks most of
   them simultaneously — which is precisely why the migration is copy-first
   (see [[file:framework-subsumption-design.org]]).
2. *State management straddles a major boundary*: riverpod 2.x (four apps),
   riverpod 3.x (two), =provider= (one), nothing (four). The kit carries no
   state dependency *by design* and enforces it with =make deps-guard=.
3. *=task-board= is the outlier that matters most*, next section.

** =task-board= — the promotion that landed and the adoption that never did

=task-board/ui= imports =desktop_kit= in *zero* files and has no =desktop_kit=
dependency at all, yet ships three widgets with the *same public class names* as
kit files:

| Widget           | Kit                               | task-board | Differing lines | Shared class names                          |
|------------------+-----------------------------------+-----------+-----------------+---------------------------------------------|
| adaptive_layout  | =layout/adaptive_layout.dart= 217 |       237 |             256 | =AdaptiveLayout=, =LayoutMode=              |
| led_indicator    | =status/led_indicator.dart= 168   |        99 |             139 | =LedIndicator=, =_LedIndicatorState=, =LedStatus= |
| resize_handle    | =layout/resize_handle.dart= 63    |        53 |              22 | =ResizeHandle=                              |

*This is not independent reimplementation — the direction is the opposite of
what the numbers first suggest.* =task-board/docs/desktop-kit-gap-evaluation.org=
(2026-07-04) inventoried both sides, found the kit had *no* layout or status
tier, and specified a two-part plan: *(A) adopt* the kit's theme / settings /
clipboard / about, and *(B) promote* =AdaptiveLayout=, =ResizeHandle= and
=LedIndicator= out of =task-board= into new =desktop_kit_layout= /
=desktop_kit_status= entrypoints, refactored to controlled widgets because the
kit forbids state-management dependencies.

Part B *shipped*: kit commit =af177de= (2026-07-04) is titled "layout+status:
promote AdaptiveLayout/ResizeHandle/SpanHost/LedIndicator". Part A never ran —
the doc's own Session State still reads =[ ] Adoption worktree=.

The divergence is therefore *explained and expected*, not drift:

- =task-board='s =AdaptiveLayout= is still Riverpod-coupled — it reads
  =ref.watch(localStorageProvider)= and writes fractions back through
  =ref.read(...)= at four call sites.
- The kit's is the *controlled refactor* the doc mandated: =required this.mode=
  with callbacks, no =WidgetRef=.

So =task-board= is the **origin** of three kit components and simultaneously the
only app that consumes none of the kit. The fork was not created by ignorance;
it was left behind by a half-executed plan.

Why this is the most instructive row in the table:

1. *Promotion without adoption doubles the surface.* The kit gained a layout
   tier and =task-board= kept its copy, so the family went from one
   implementation to two. Any consolidation that promotes code without a
   *gated* adoption step reproduces this exactly.
2. It is the cheapest migration pilot available — no kit history to unwind, no
   pin to renegotiate, three commits total, and already on Riverpod 3 (the
   chosen standard).
3. Its =Part A= list (theme → =DeskTheme=, =local_storage= → =SettingsStore=,
   clipboard, About, =Foldable=) is a *pre-written, evidence-backed migration
   script* that should be executed rather than re-derived.

The governing lesson for =frameworks=: the copy-first invariant must include an
explicit *retire-the-fork* step with a verification gate, or the migration ends
in the =task-board= state — a correct shared implementation that nobody consumes.

** Reading the table — five recurring shapes

Every application independently grew the same five things. This is the
=app_kit= tier's requirement list, derived from the table rather than
guessed:

1. *App shell / chrome* — =app_shell= in voicelab (1392), alert-log
   (53), mail-sweep (103), task-board (118); =shell= in ghk_dashboard (399) and
   netroute_manager (116); =chrome/= in textloom. Nine of eleven apps. The kit has *no
   shell tier at all* — it stops at =adaptive_layout=/=span_host=.
2. *Settings presentation* — =settings_pane= 3157 / =settings_page= 914 /
   =settings_view= 433, 309, 161 / =settings_screen= 53, 48 / =categories= 165,
   149 / =settings_categories= 590. Every app. The kit has
   =settings_presentation= 686 + =settings_store= 157, and the two largest app
   surfaces bypass them.
3. *Theme entry point* — =theme= 601, 262; =app_theme= 81, 79; =notif_palette=
   188; =theme_providers= 124; =theme_provider= 35; =emacs_face_theme= 176. The
   kit has =desk_theme= 445 + =appearance_pane= 1004; apps re-derive the
   *wiring*, not the palette maths.
4. *Status / connection affordance* — =connection_banner= 91, 49;
   =status_badge= 35; =status_chip= 39; =state_strip= 326; =led_indicator= 99;
   =service_status_card= 94; =update_banner= / =restart_banner=. Kit has only
   =led_indicator= 168.
5. *About / version* — kit 231, voicelab 221, ghk 50, word-bank 27.

Items 1–3 are absent or incomplete in the kit and present in nearly every app:
that is the gap =frameworks/ui/pkg/app_kit= exists to close. Items 4–5 exist in
the kit and are re-implemented anyway: that is a *discoverability* gap, and
=cmd/ui0= is the answer to it (a capability with no =ui0= surface is not
discoverable, hence not done).

*Caveat on item 1, established by the =task-board= case above:* "the kit has no
shell tier" was true when the 2026-07-04 evaluation was written, and the kit has
since gained =layout/= (=adaptive_layout=, =resize_handle=, =span_host=) and
=status/= (=led_indicator=). The remaining absence is the *shell* proper —
=app_shell= / =shell= — which nine of eleven apps hand-roll and the kit still
does not provide. Do not infer the other four shapes are unaddressed without
re-checking the kit tree; one of five has already been half-closed.
