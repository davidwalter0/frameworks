** Where honouring high-contrast belongs

Traced the theme package's contrast machinery to find the right seam:

- ~lib/src/theme/contrast.dart~ — WCAG primitives. ~kMinContrast = 3.0~ (the
  AA floor for large text / UI components) and ~isLegibleOn(fg, bg)~, a

- ~lib/src/theme/apca.dart~ — the perceptual (WCAG-3 draft) companion metric,
  with size/weight-aware floors (~apcaTextFloor~) and a flat non-text floor

  kApcaNonTextFloor})~. **Every one of these already takes its target as a
  parameter** — the machinery to switch to a stricter target exists; nothing
  currently sets it from context.

  wires all of the above into a ~ThemeData~. It calls ~isLegibleOn(fg,

// Probe for the suspected double-scaling defect in
// ui-kit-private's lib/src/theme/ui_scale.dart (applyUiScale).
//
// Question: with an ambient MediaQuery textScaler simulating the desktop's
// xdg-desktop-portal `text-scaling-factor` (1.25) already in the tree, and
// the kit's applyUiScale() applying a user-chosen in-app scale of 1.2 on top
// of it, does the resulting effective textScaler:
//   (a) discard the system factor and read exactly 1.2  (override), or
//   (b) compound to 1.25 * 1.2 = 1.5                    (multiply)?
//
// Method: pump a widget tree with an explicit outer MediaQuery
// (textScaler: TextScaler.linear(1.25)) standing in for what the engine
// would normally surface from the desktop portal, wrap the child in
// applyUiScale(context, 1.2, child), and read back MediaQuery.textScalerOf
// from BELOW the wrapper — i.e. from the actual child's BuildContext, which
// is what any real widget under the wrapper would see and use to size text.

import 'package:desktop_kit/desktop_kit_theme.dart';
import 'package:flutter/material.dart';
import 'package:flutter/rendering.dart';
import 'package:flutter_test/flutter_test.dart';

void main() {
  testWidgets(
    'applyUiScale: does the user scale override or multiply the ambient '
    'system text-scaling factor?',
    (WidgetTester tester) async {
      const double systemFactor = 1.25; // stand-in for the desktop portal's
      // org.gnome.desktop.interface/text-scaling-factor, as surfaced by the
      // engine into the ambient MediaQuery before any app code runs.
      const double userScale = 1.2; // the kit's applyUiScale() argument,
      // e.g. driven by AppearanceSettings.uiScale / DisplayConfig.uiScale.

      TextScaler? effectiveScaler;
      double? effectiveFontSize;

      await tester.pumpWidget(
        MaterialApp(
          builder: (BuildContext context, Widget? child) {
            // Outer MediaQuery: simulates what the Linux embedder already
            // put in the tree from xdg-desktop-portal, ABOVE any kit code.
            return MediaQuery(
              data: MediaQuery.of(context).copyWith(
                textScaler: TextScaler.linear(systemFactor),
              ),
              child: applyUiScale(
                context,
                userScale,
                Builder(
                  builder: (BuildContext innerContext) {
                    // Read the textScaler BELOW applyUiScale's wrapper --
                    // exactly what a real Text widget in the app would see.
                    effectiveScaler = MediaQuery.textScalerOf(innerContext);
                    effectiveFontSize =
                        effectiveScaler!.scale(14.0); // arbitrary base size
                    return const Text('probe');
                  },
                ),
              ),
            );
          },
          home: const SizedBox.shrink(),
        ),
      );
      await tester.pumpAndSettle();

      // Independently confirm via the RENDERED text size, not just the
      // MediaQuery value, so the assertion is not trusting one accessor.
      final RenderParagraph paragraph = tester.renderObject(
        find.text('probe'),
      );
      // fontSize as laid out reflects TextPainter's applied text scaler.
      final double appliedScaleFromRender =
          paragraph.text.style!.fontSize == null
              ? double.nan
              : effectiveFontSize! / 14.0;

      // ---- Report ----
      // Print unconditionally so the evidence is visible in the test log
      // regardless of which branch the assert takes.
      // ignore: avoid_print
      print(
        'systemFactor=$systemFactor userScale=$userScale '
        'effectiveScaler=$effectiveScaler '
        'effectiveFontSize(base=14)=$effectiveFontSize '
        'impliedCompositeFactor=$appliedScaleFromRender',
      );

      const double overrideExpected = userScale; // hypothesis (a): 1.2
      const double multiplyExpected =
          systemFactor * userScale; // hypothesis (b): 1.5

      final double got = effectiveScaler!.scale(1.0);

      if ((got - overrideExpected).abs() < 0.001) {
        // ignore: avoid_print
        print(
          'RESULT: (a) OVERRIDE -- the system text-scaling-factor is '
          'DISCARDED; effective factor is exactly the user scale '
          '($overrideExpected).',
        );
      } else if ((got - multiplyExpected).abs() < 0.001) {
        // ignore: avoid_print
        print(
          'RESULT: (b) MULTIPLY -- the two factors COMPOUND; effective '
          'factor is $multiplyExpected.',

        // ignore: avoid_print

      expect(

            'the system factor with the user scale (hypothesis (b)) -- '

**(a) OVERRIDE occurs, confirmed by test, not inference.** The ambient
1.25x desktop factor is silently discarded the moment ~applyUiScale~ runs
with any ~scale != 1.0~; the effective factor is exactly the user's 1.2,
never 1.5.

**Important asymmetric detail, also confirmed by reading the code (line 47):
~if (scale == 1.0) return child;~** — at the user's *default* slider value
(no override), ~applyUiScale~ returns the child completely unwrapped, so the
ambient system factor passes through untouched. **The defect only manifests
once the user touches the in-app zoom control away from 1.0** — at that
point the OS accessibility setting they may depend on (larger text for low
vision) is silently replaced rather than built upon. In the concrete
example numbers, a user who explicitly set 1.25x at the desktop level and
then nudges the in-app zoom to 1.2x ends up with text *smaller* than their
OS setting alone would have given them (1.2 < 1.25) — with no indication
anything changed relative to what they expect ("I only asked for a small
in-app bump").

** Recommended composition, and the argument against it

*** Recommendation: compose (multiply), not override

~scale~ should multiply the *ambient* scaler's effect at every font size,
not replace it. Concretely, ~TextScaler~ has no built-in "compose two
scalers" helper — verified against the framework source,
~$HOME/flutter/packages/flutter/lib/src/painting/text_scaler.dart~:
the only combinator is ~TextScaler.clamp({minScaleFactor, maxScaleFactor})~,
which bounds one existing scaler's *output range*; it does not multiply two
scalers together. So the fix needs a small custom ~TextScaler~:

Argument FOR composing:
- Respects a signal the user (or their desktop environment's defaults for an
  accessibility profile) explicitly configured at the OS level — silently
  discarding an assistive-tech preference is the more severe failure mode of
  the two, on accessibility grounds specifically: this preference commonly
  exists *because* the user has a vision need, and an app-level control
  silently overriding it removes accommodation the user didn't know was
  contingent on which slider they touched.
- Matches the common mental model for an in-app "zoom" layered on top of
  whatever the desktop already does — the same stacking behaviour as
  browser zoom on top of OS-level font scaling, which is the closest
  existing UX precedent for "in-app scale control on a desktop OS".
- The asymmetry documented above (defaults pass the system factor through,
  only non-default breaks it) is itself evidence this is an oversight rather
  than a considered choice: a deliberate "override" design would more
  likely have been unconditional, not conditional on whether the user
  happened to touch the slider.

Argument AGAINST composing (the real counter-case, not a strawman):
- ~ui_scale.dart~'s own doc comment states this is a **"pragmatic desktop
  zoom, not a geometric one"** — text and ambient icon size scale, but
  layout geometry, containers, paddings, and images do NOT. Composing two
  large factors (e.g. a desktop set to 2.0x for a low-vision user, times a
  1.5x in-app zoom = 3.0x) grows text far more than the non-scaling
  container it sits in was ever budgeted for, which is a MORE likely
  overflow/clipping failure under composition than under override, exactly
  because this module explicitly opted out of resizing the geometry that
  would normally absorb it.
- A user who deliberately sets an *absolute* target in-app (some apps'
  "reading size" pickers show literal preview text at each option) may
  reasonably expect that value to be deterministic regardless of desktop
  settings, especially in a kiosk-style or fixed-viewport desktop app where
  predictability of the rendered size matters more than composability.
- **Mitigation, not rebuttal**: the ~.clamp(maxScaleFactor: ...)~ in the
  proposed diff exists specifically to bound the failure mode above — it
  keeps the "respect the OS setting" property while capping how far the
  *product* of the two factors can run before this module's known geometry
  limitation bites. This is a genuine trade-off resolution, not a dismissal
  of the counter-argument: composing without a ceiling would be worse than
  either (a) or (b) in the worst case (unbounded compounding across

* Glossary
- portal :: xdg-desktop-portal, the Linux desktop settings/accessibility
  D-Bus service the Flutter engine reads from.
- APCA :: Accessible Perceptual Contrast Algorithm — the WCAG-3 draft
  perceptual contrast model used alongside flat WCAG 2.x ratios in this kit.
- HCT :: Hue-Chroma-Tone colour space (Material's ~material_color_utilities~
  package) used for hue-preserving contrast walking.
- TextScaler :: Flutter's abstraction (replacing the deprecated
  ~textScaleFactor~ double) for computing a scaled font size from an
  unscaled one; supports non-linear scaling in principle.
