* 1. The finding that reframes the question

The governing principle
([[file:../../docs/architecture-and-process-design.org]] §1, Direction 1) is
that byte-identical text can be *coincidence* — two independent minimal
implementations of one small idea — and that merging coincidence manufactures a
coupling which did not exist. That principle is correct and it is the right
test to apply. Applying it here produces an unexpected result:

*Not one of these 18 pairs is coincidental identity. Every pair has a known
copy direction and a known date.*

| Set | Provenance | Evidence |
|-----+------------+----------|
| A (kit ↔ voicelab) | voicelab wrote it; the kit *promoted* it 2026-07-02 | kit commit =c3932e4= "feat(kana): promote romaji/kana engine + mark/text-motions from voicelab"; voicelab file dates to =af6f7a5= 2026-06-07 |
| B (example/ ↔ textloom) | a single fork event, 2026-07-19 | textloom root commit =bd6fd4f= "eedit: fork the example gallery into a standalone lightweight editor" |

Two consequences, and both change how the verdicts should be read.

*First, "merging creates a coupling that did not exist" does not apply to any
pair in this set.* The coupling already exists — one file IS the other — and it
is already decaying: of the 34 filenames =example/lib= and =textloom/lib= share,
16 are identical and *18 have diverged in ten days*, textloom larger in all 18
(measured; see §6). Identity here is not convergence, it is a snapshot with a
timestamp.

*Second, LEAVE therefore never means "keep two live copies".* For a fork there
is no independent derivation to protect, so every LEAVE below means one of:

- *LEAVE (one owner)* — the file is demo/gallery material or app-local wiring;
  exactly one side keeps it, and the other side's copy is dead or dies with its
  page.
- *LEAVE (retire against existing)* — the decision is *already owned* by tier 1
  under a different name, so the app copies are the duplication and the fix is
  deletion, not promotion. Promoting would install a second implementation in
  the same package.

Reading LEAVE as "leave both alone" would preserve precisely the drift the kit's
own Makefile already condemned when it dropped the pre-split =eedit/= subtree:
"the copy that stayed behind was never removed and had drifted badly. Checking a
stale duplicate proved nothing and hid real drift."

*Where the principle DOES bite in this family* is the case the census cannot
see: identical text that encodes a *composition* each app must own. There is
exactly one such file here — =keymap_setup.dart= (§3.5) — and the reason it must
stay forked is not the reason the hypothesis gave.

* 3. Where I disagree with the starting hypothesis

This is the section to read if you read only one. Five disagreements, in
descending order of how much they change the plan.

** 3.1 =org_fold_model.dart= — MERGE tier 1 → *LEAVE (retire against existing)*

The hypothesis reads it as "library code, nothing gallery-specific", and on
content alone that is right: pure Dart, no Flutter, a parser and a fold model.
The hypothesis's own doubt was about the directory name. The directory name is
*not* the deciding fact, and the real one is stronger:

The kit already contains, in =lib/src/org_edit/org_outline.dart=:

: List<OrgNode> parseOrgOutline(String text)

=org_fold_model.dart= defines:

: List<OrgHeadingNode> parseOrgOutline(List<String> lines)

*Same function name, same job, different node type* — plus =OrgFold.headings()=
in =lib/src/org_edit/org_fold.dart=, a third answer to "what is an org
heading", which both apps' =emacs_buffer_editor= already uses heavily.
Promoting this file puts two =parseOrgOutline= functions and a third outline
node type into one package. The decision is already owned by tier 1; the app
copies *are* the duplication. This is a delete-and-adopt, not a merge, and
scheduling it as a merge would make the kit worse.

** 3.2 =org_fold_example.dart= — MERGE tier 1 → *LEAVE (as written)*

The hypothesis flagged the =example/= directory name as the counter-argument.
The directory name is a weak signal (=org_fold_example= is live in *both* apps'
settings "Folding" category — it is not dead scaffolding). The strong signal is
the widget's *signature*:

: const OrgFoldExample()      // no value in, no onChanged out

It parses a hardcoded =kSampleOrg= in =initState=. Tier 1's admission rule —
"takes its state as =value= and emits =onChanged=" — is failed by construction,
not by accident. And the file's own header says it exists to prefer "notekeep's ▸
(collapsed) / ▾ (expanded) Unicode triangle glyphs … truer to the Emacs
org-mode look than desktop_kit's chevron-based =Foldable=" — i.e. it encodes a
*taste disagreement with a kit widget*. Merging it puts both opinions in the
kit.

*The fact that would flip this:* refactor it to =OrgFoldOutline({required String
text})= and move the sample out to a shared fixture. Then it is the same shape
as =faces_preview= and belongs in tier 1 for the same reason. As written, it is
not mergeable — and that distinction matters, because "merge after a refactor"
and "merge" are different amounts of work sitting in different tranches.

** 3.3 =emacs_help.dart= — a merge that must *reconcile*, not *add*

Not in the hypothesis, and the most likely way this migration quietly gets
worse. The kit already ships a keymap help dialog:
=lib/src/keymap/keymap_help.dart=, 192 lines, "Generalised from notekeep's
=speed_help.dart=", data-driven — *each app hands it groups*.
=emacs_help.dart= (202 lines) does the better thing: it derives the groups from
the live =KeymapConfig= + =KeymapRegistry=, so a rebound key is reflected
without the app maintaining a parallel list.

Both are right about their own goal, and both are =describe-bindings=. Copying
=emacs_help.dart= into tier 1 alongside =keymap_help.dart= produces *three*
implementations of one dialog — the =about_dialog= discoverability failure the
census already recorded, repeated inside the fix for it. Verdict stands at MERGE
tier 1; the exit criterion must name =keymap_help.dart= as absorbed or deleted.

** 3.4 =emacs_syntax_samples.dart= — LEAVE (fixture) → *MERGE tier 1*

The hypothesis is that this is demo fixture content, and half of that is true —
it *is* content: four short source snippets. But apply the test rather than the
category. The file's payload is:

: final Map<SyntaxLanguage, String> kSyntaxSamples = { ... }

keyed on =SyntaxLanguage=, which the *kit* owns (=desktop_kit_syntax=). Add a
language to the kit and every copy of this map must gain an entry or its preview
silently renders blank for the new language. "If this decision changes, must
both change?" — yes, and *because the kit changed*. That is the merge test
passing, on content.

It is not a hypothetical. =textloom/lib/widgets/editor_settings_pane.dart= carries
this comment, in the file itself:

#+begin_quote
The canonical =SyntaxLanguage= set — the same one =SyntaxFaces=, =FacesPreview=
and the re_editor panel speak. go / org / yaml were unreachable while this pane
offered a locally-invented enum.
#+end_quote

That is a recorded incident of exactly this drift, in exactly this cluster. It
also is not gallery-only: textloom reaches =kSyntaxSamples= from its live settings
pane via =FacesPreview='s default sample.

*Caveat kept honest:* the samples' *taste* (which snippet demonstrates a
language) is genuinely editorial. The merge should therefore make the map
overridable per call — which =FacesPreview= already supports with its optional
=sample= parameter. Shared default, app override; the completeness obligation
travels with the enum, the taste does not.

** 3.5 =keymap_setup.dart= — LEAVE agreed, but the stated reason is wrong

The hypothesis says "each app's own binding choices". The file contains no
binding choices. Its entire body is three one-line compositions:

: KeymapRegistry.defaults(); registerKanaActions(registry);
: withKanaDefaults(KeymapConfig.fromDefaults(registry));
: kanaTestEffects();

The =ToggleKanaIntent=, the bindable action, the *default Shift-K binding* and
the transform all live in =desktop_kit_kana_keymap.dart= — the file's own header
says so. So if bindings were the reason, the kit would already be violating it.

The real reason is the one this exercise was set up to find: *merging would force
the kit to hold an opinion it deliberately declined.* =desktop_kit_kana_keymap=
is an **opt-in** module precisely so the core keymap stays IME-free; a shared
"defaults plus kana defaults" helper makes kana effectively on-by-default for
whoever calls the convenient thing.

And the composition genuinely varies — measured across the family, not assumed:

| App | Composition |
|-----+-------------|
| example / textloom | =defaults= + =registerKanaActions= + =withKanaDefaults= |
| word-bank | the same *plus* =registerAnthyActions=, inside a Riverpod provider |
| voicelab | =KeymapRegistry.defaults()= + its own kana overlay (=kanaKeymapRegistry()=) |

Four apps, three compositions. The kit correctly ships the pieces and not the
assembly. *Separate defect, not a merge:* textloom's production code calls
=buildExampleRegistry= / =exampleDefaultConfig= (=lib/settings_categories.dart=
plus 6 test files) — "example"-named functions in a shipped app. That is a
rename, and it is the kind of artifact that makes a fork legible.

* 4. The edge cases, answered

** 4.1 Data rather than code: does "shared fact" beat "nobody should own this"?

*A shared fact still needs an owner, and the owner is whoever owns the pipeline
that consumes it.* "Nobody should own this" is a real instinct but it argues
against *duplicating* a fact, not for it — and it dissolves the moment the fact
stops being purely factual.

=x11_colors.dart= is the case in point, because it is not purely factual. It
documents five names (=green=, =gray=, =grey=, =maroon=, =purple=) where raw X11
=rgb.txt= and CSS Color 4 disagree, and it *chooses* CSS. That is a policy. Two
copies of a policy means the same =.emacs= can render differently in two apps of
one family — a divergence with no owner to arbitrate it. Merged, the deviation
has one documented home; forked, it is a coincidence waiting to stop being one.

The mirror case is in the same set: =org_header_theme.dart='s named palettes are
published theme colours (fact) *and* a per-level assignment the file's own
verification note calls "an editorial choice, not part of any spec". Fact and
taste in one file is why that verdict carries a carve-out rather than being
atomic.

** 4.2 Coincidental identity today, different purpose tomorrow: what happens at
   the first divergence, merged vs forked?

For =keymap_setup= the asymmetry is decisive. *Forked*, the first divergence
costs one app a one-line edit and the other nothing — because there is no shared
thing to negotiate. *Merged*, the first divergence forces a choice between three
bad moves: add a flag to a shared helper (=withKana=, then =withAnthy=, then
=withoutKana=), fork it back out (having paid for the merge twice), or let the
kit's opt-in IME module become the default. The measured evidence that this is
imminent rather than hypothetical is that it has *already* diverged three ways
across four apps (§3.5); example↔textloom agree only because one is ten days old
and copied from the other.

Contrast =text_motions=, where the same question resolves the other way. Its one
judgement — "treat all non-ASCII as a word char, so M-f over Japanese advances
sensibly" — will eventually want a real syntax table. *Merged*, that arrives as a
parameter on one function and every caller benefits. *Forked*, one app gets a
syntax table and the other keeps a subtly different =M-f=, and nobody notices
because both are "correct". Same shape of question, opposite answer, and the
discriminator is whether the divergence is a *per-app choice* (keymap
composition) or a *refinement of one shared rule* (word boundaries).

=editor_shell_page=, no =org_highlight=, no =re_editor_panel=, and no
=re_editor= dependency. Their tests came along, so a test suite reports them
"used" while the app cannot reach them — which is why a grep for the symbol name
answers this question wrongly and a grep restricted to =lib/= answers it right.

So the general answer is: *a preview is library code when a second application
genuinely renders it*; a preview with one real consumer is that application's
code, per the standing one-consumer rule. Naming it "preview" decides nothing.
Note the direction of the risk: these two are the pairs most likely to be
merged on appearance, since they are the best-behaved widgets in the set.

** 4.5 Why nothing here is tier 2

Tier 2 (=app_kit=) is the app-shell tier: Riverpod 3 permitted, opinions
permitted, ≥2 hand-rolled consumers required for admission. Measured: *none* of
these 18 files imports Riverpod (textloom does not depend on it at all), and none of
them is shell code — they are primitives, dialogs, previews, a colour table and
one wiring adapter. The only file that wants to *hold an opinion* is
=keymap_setup=, and it fails admission for the opposite reason: its composition
is not shared across ≥2 apps (§3.5 measures three compositions across four

Corollary worth recording: this byte-identical bucket contributes *nothing* to
=app_kit=. Tier 2's contents still have to come from the census's five recurring

** 4.7 The elisp engine's growth path — does it move any of these merges?

*STATUS: context, not a decision.* Prompted by text reaching this agent mid-turn
about an elisp compiler/interpreter/tooling option and "still room to grow the
tool" — same provenance caveat as §4.6. The question is worth answering on its own
merits regardless of who asked: six of the eighteen files sit on the
Emacs-config→UI pipeline, so a future engine *could* have moved them, and the
right response is to check rather than assume. What follows is measurement of what
is on disk plus the conclusion that nothing moves.

*Answer: it moves no verdict. It makes two of them more robust, sharpens one
prerequisite, and improves the destination of one carve-out.* The reason is that
these files sit on the *consumption* side of a config value, and an engine changes
how the value is *obtained*.

What exists today, measured:

| Artifact | What it is |
|----------+------------|
| =~/go/src/git.savannah.gnu.org/emacs= | *upstream* GNU Emacs checkout (real upstream commits; the doc pins =0a714557ebd= = =emacs-31.0.91-403=). Reference / oracle, not our code. |
| =…/docs/emacs-lisp-engine-architecture.org= | 544 lines, status *Complete* (2026-07-26): value representation, reader→evaluator→bytecode→native pipeline, specpdl / non-local exit, GC, plus a *port surface* scoping a Go reimplementation in tiers 0–4 |
| =…/docs/emacs-ui-architecture.org=, =…/emacs-architecture-overview.org= | the editor half — the engine is *369* of Emacs's 1,842 primitives |
| =…/docs/mcp-ast-coverage-gaps-emacs-corpus.org= | the same tree already used as an *AST corpus* |
| =desktop_kit_elisp_eval.dart= + =src/elisp_eval/elisp_eval.dart= | 494 lines *already in the kit* — a deliberately tiny, side-effect-free =M-:= evaluator over the kit's own sexp reader; opt-in, not re-exported from =desktop_kit.dart= |

So the state is *scoped, not built*: the port surface says it states "the
*obligations*, not a design", its Next Steps gate the tier decision on a
prior-art survey (mgmt =46e79c9d=, =071f4c16=), and it flags an unresolved fork —
*interpreter vs translator*, since mechanically converting selected elisp to Go
"may serve … at a fraction of the cost". Nothing here is ready to depend on, and
nothing in tranche 3b is blocked by it.

*Effects on the verdicts:*

1. =x11_colors= and =emacs_face_theme= (both MERGE tier 1) — *robust, not a bet.*
   An engine changes how a face's =:foreground= is obtained (scrape → evaluate);
   it does not change that ="cornflowerblue"= must become a =Color=, nor that
   =faceToThemeSlot= maps face names to scheme slots. Both merges are needed under
   either future. This matters because "an engine is coming" is exactly the
   argument that would defer them — and deferring keeps two copies of a *policy*
   (§4.1) across a change that does not touch it.
2. =emacs_face_theme='s prerequisite — *sharpened.* Its =faceColor= /
   =faceTextStyle= dependency lives in =emacs_seed_bridge.dart=, the harvest-side
   seam an engine is *most* likely to subsume. Promote those two functions *beside
   the colour data*, not beside =ConfigHarvester= — otherwise the promotion lands
   in the one file most likely to be replaced.
3. =org_header_theme='s carve-out — *strengthened, with a better destination.*
   =kDavidOrgHeaderConfig= + =davidOrgPaletteFromConfig()= run
   =ConfigHarvester().harvest(...)= over one person's =custom-set-faces=. Under an
   engine that string becomes a *conformance fixture* — and a far better corpus is
   already on disk and already used as one: =emacs/lisp/**/*.el= in the upstream
   checkout. Fixture out of tier 1 either way; when it moves, prefer the real
   corpus to one config.
4. Everything else — untouched. *None of the 18 adjudicated files imports
   =elisp_eval=*: the only consumers in either app are the two
   =emacs_buffer_editor.dart= copies, which are *diverged* files and out of scope
   (measured).

*One boundary not to pre-empt.* =desktop_kit_elisp_eval.dart= states verbatim that
config seeding "does NOT execute the config — bundling an executor here would
contradict that stated boundary", and stays opt-in for that reason. That boundary
is precisely what an engine would move, and moving it is the kit's call, not a
side-effect of a merge. Worth saying because merging =x11_colors= *into* the
harvest pipeline could be misread as a step toward execution. It is not: a colour
table resolves data and evaluates nothing.

*A fourth instance of the pattern this document keeps hitting.* The kit already
owns a small version of the thing the apps grew — =keymap_help= vs =emacs_help=
(§3.3), =parseOrgOutline= vs =org_fold_model= (§3.1), =Foldable= vs
=org_fold_example= (§3.2) — and now a 494-line =elisp_eval= against an
engine-scale ambition. In the first three the kit's version is the one to keep or
absorb into; the elisp case is the one where the *ambition* is the larger thing
and the kit's tiny evaluator is the honest floor. Recorded as context, not a
verdict: =elisp_eval= is not among the 18.

*One thing this does NOT decide (b).* Whether the engine should be an interpreter
or a translator, and whether it targets =.el= or the 168-opcode =.elc= VM. Those
are the engine epic's own open questions (=46e79c9d=), they are gated on a
prior-art survey, and no verdict here leans on the answer.

one. If no, it stays private in the gallery and the question is closed. Today it
is =_=-private, so it is not reusable either way, and I am not going to invent a
tier for it.

* Glossary
- coincidental identity :: two byte-identical files with *independent*
  derivation — each the obvious minimal implementation of the same small idea.
  The case where merging manufactures a coupling. Measured absent from this set.
- fork snapshot :: byte-identical files with one known copy direction and date.
  The coupling already exists; identity is a timestamp, not a property.
- retire against existing :: delete a duplicate by adopting code the shared tier
  *already has*, rather than promoting the duplicate. Reduces total surface.
- one-consumer rule :: a package/component with exactly one real consumer is
  that project's code, not shared infrastructure. Tier 2's admission gate, and
  applied here to previews whose second consumer turned out to be a test.
- live consumer :: an import reachable from a package's =lib/=. A =test/=-only
  import is not one, and conflating the two is how a dead widget reads as shared.
