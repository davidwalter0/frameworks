* 0. Method recap and exclusion set

Same method as the rest of [[file:duplication-census.org]] ("How to read this
document" read first, taxonomy not re-derived here):

| Cause  | Meaning                                              | Remedy                                    |
|--------+-------------------------------------------------------+--------------------------------------------|
| STALE  | app predates/lags the kit; kit copy newer and larger  | delete app copy — an upgrade              |
| AHEAD  | app copy is newer than the kit's                     | port delta into kit first, then delete    |
| ORPHAN | promoted app→kit, adoption never executed            | run the adoption                          |
| ABSENT | no kit equivalent; two+ apps forked in parallel      | design the shared component from the union |

Two diff measures, as before: unsorted =diff | grep -c '^[<>]'= approximates
patch size (order-sensitive); sorted =diff <(sort A) <(sort B)= is the
set-difference (order-insensitive, answers "is this the same code"). Every
table below states which is used; sorted is used throughout except where
noted, because most pairs here are independently-authored, not
literal-copy-then-edit, so unsorted edit distance would overstate divergence
from reordering alone.

*Exclusion set, applied to every =find=/=grep= below:* =vendor/=,
=.worktree/=, =dist/=, =*.freezed.dart=, =*.g.dart=. One additional case not
covered by that pattern: =netroute_manager= ships 4 generated protobuf files under
=lib/src/generated/lbmanager/v1/= (=lbmanager.pb.dart= 1388,
=lbmanager.pbenum.dart= 61, =lbmanager.pbgrpc.dart= 187,
=lbmanager.pbjson.dart= 342 — 1,978 lines, header literally reads "Generated
code. Do not modify."). None of the four share a basename with any other
source in this census, so excluding them changes no finding, but they are
flagged here because the brief's hygiene warning is specifically about counts
that include generated code unlabeled — this is the concrete instance for
this extension. All counts below are on the excluded set (dart-file counts
per app, confirmed against the brief): nh 60→50 real (10 generated), gu 32,
gd 26, lb 22 (of which 4 are the generated protobuf, 18 hand-written), ghk 36.

** Reading these — three are NOT forks, one is

*=host_ui_font.dart= — ORPHAN, already resolved.* Kit's own docstring says it
directly: /"Ported from alert-log — the app-side Riverpod
=hostUiFontProvider= is intentionally OMITTED so the core stays
state-management agnostic."/ nh's 18-line remainder is the thin Riverpod glue
+ a re-export of the kit's =detectHostUiFont=/=parseGnomeFontName=. This is
the *rare* case of a promotion that also got its adoption step completed —
the same class of event as the =task-board= ORPHAN in
[[file:duplication-census.org::*5. The =task-board= ORPHAN]], except this one
finished. Not a finding requiring action.

*=presets.dart= — legitimate customization, not staleness.* nh imports kit's
=ThemePreset=/=NamedColor= types and kit's shared foreground/background
swatch lists (re-exported, "so the Appearance pane keeps a single
theme/presets import"), then *hides* kit's own =kThemePresets=/=presetByName=
to substitute an app-specific list bound to =NotifPalette= (a =DeskPalette=
subclass carrying per-notification-type colours the kit has no reason to
know about). Kit being larger reflects kit owning more preset variety, not nh
lagging — nh's file is doing something kit's isn't (palette-typed binding).
Classify as *ABSENT* only in the narrow sense that "a NotifPalette-bound
preset list" has no kit equivalent by construction (it's app-domain-specific)
— **not** a candidate for deletion.

*=appearance_pane.dart= — same pattern, larger scale.* nh's docstring:
/"Hide desktop_kit's own preset list/helper — this app uses its
NotifPalette-bound list from theme/presets.dart (same ThemePreset type,
different data)."/ This file is *already counted* in
[[file:duplication-census.org::*Settings persistence and presentation]]'s
513-line entry for alert-log — this cross-check adds the
classification that entry lacked: *not staleness, a deliberate customization
layer over the kit's generic pane.* No action implied.

*=version_info.dart= (mountbridge) — genuine STALE, new finding.* Kit's version
is a documented, generalized superset: same three fields (=version=,
=commit=, =date=), same =displayString= getter behaviour, but kit defaults
empty-string instead of gd's =\'unknown\'= fallback, and kit's
=VersionInfo.fromMap= is a drop-in replacement for gd's
=VersionInfo.fromDbusMap= (same map-shape, same null-safety fallback
pattern) — verified by reading both factories in full. This *is* a case
where the app copy predates the kit's generalization and is a strict subset;
deleting gd's copy in favor of =desktop_kit='s (with call sites switched from
=.fromDbusMap= to =.fromMap= and the =\'unknown\'= display fallback ported in,
a few lines) is a safe upgrade. 27 lines removed, no functionality lost.

**Why =main.dart= is not evidence of a fork here, unlike textloom's.** textloom's
=main.dart= was *958* lines — bigger than the example's own 557, because
textloom's =main.dart= absorbed the whole gallery-navigation shell the example
provides. Each of these five apps' =main.dart= is 32–108 lines: a normal,
single-purpose Flutter entrypoint (=runApp=, provider/DI wiring, one
=MaterialApp=). A shared basename between any two Flutter apps' entrypoints
is close to unavoidable and carries no signal by itself; the *direction and
magnitude* (all five are 5×–17× *smaller* than the example, never larger) is
what rules out the textloom shape here. If any of these apps' =main.dart= had
come in *larger* than 557 and absorbed gallery-style page routing, that would
have been the signal to chase — none did.

**=metrics.dart= is a coincidental namesake, confirmed by reading both.**
example's =contrast_lab/metrics.dart= computes WCAG contrast-ratio metrics
for the theme-lab demo. nh's =core/models/metrics.dart= is a =freezed=
data class (=AppCount=, =Metrics= with =ingested=/=deduped=/=rateDropped=/
etc. fields) describing the notification-capture pipeline's counters. Same
noun, unrelated domains, unrelated code. No finding.

**Aggregate for this section: zero new example-forks found.** The blind spot
this task exists to close — an adoption-ratio measure being unable to see a
fork of =example/=, because =example/= isn't =desktop_kit= — does not recur
in any of these five apps. This is worth stating with the same confidence as
a positive finding: it was checked, by the same method that caught textloom, and
came back clean.

* 7. Recommendation — where this fits in the tranche order

1. *=mountbridge= =version_info.dart= (STALE, §1)* is the cheapest, lowest-risk
   item in this entire extension — 27 lines, a strict subset, a two-call-site
   edit (=.fromDbusMap= → =.fromMap=, adjust the empty-vs-\'unknown\' display
   fallback). Bundle it with whatever tranche is already touching mountbridge;
   it doesn't need its own tranche.

2. *The badge/chip/pill cluster (§4.1) and the banner cluster (§4.2)* are
   the next-cheapest wins with the best payoff-to-risk ratio: small absolute
   size (132 + 376 = 508 lines), three apps each, and a clean "design one
   shared widget from the union, thin call sites everywhere" remedy — the
   textbook ABSENT case. Recommend a single small tranche, "kit: promote
   PaletteBadge + StatusBanner," ahead of the larger architectural work,
   both because it is self-contained and because it demonstrates the
   filename-blind method's payoff concretely (worth doing before the bigger,
   harder tranche below so the team sees a fast win from the extended
   method).

3. *The =netroute_manager=/=ghk_dashboard= scaffold (§3.2) and the
   =alert-log=/=mail-sweep= scaffold (§3.1)* are the two large,
   hard items this extension surfaced, and they are harder than a typical
   STALE/AHEAD tranche because neither is a strict subset of the other —
   both require designing a shared primitive from the union of two live,
   diverged implementations (per the ABSENT remedy), not a mechanical
   delete. Recommend these as their *own* tranche(s), scheduled *after* the
   existing [[file:framework-subsumption-design.org]] tranches that are pure
   STALE/AHEAD deletes (mechanically cheaper, should land first per the
   copy-first invariant), but *before* any tranche that would touch
   =netroute_manager= or =ghk_dashboard='s app-shell code for unrelated reasons —
   touching that code twice (once for an unrelated fix, once for this
   consolidation) is exactly the kind of avoidable double-cost the existing
   census's "promotion without adoption" lesson warns about. Two apps, two
   different state-management idioms in play across the family (Riverpod
   for nh/gu, raw =InheritedNotifier= for lb/ghk) — the union design should
   decide *once* whether the kit-level primitive is state-management
   agnostic (like =SettingsStore= already is) rather than picking a side.

4. *The sortable-table shape (§4.4)* rides along with whichever of (2) or
   (3) lands first that touches nh, lb, or ghk — it is not large enough on
   its own to justify a fourth tranche, and gd's 157-line slice is small
   enough to fold into whichever tranche touches gd for the =version_info=
   fix.
