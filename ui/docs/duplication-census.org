* How to read this document

Duplication in this family has *four distinct causes*, and they take opposite
remedies. Sorting by line count alone produces the wrong work order, so every
entry below is classified:

| Cause | Meaning | Remedy |
|-------+---------+--------|
| *STALE* | app predates the kit; the kit copy is newer and larger | delete the app copy — an *upgrade*, expect behaviour change |
| *AHEAD* | the app copy is newer than the kit's | port the app's delta *into* the kit first, then delete |
| *ORPHAN* | promoted app→kit, adoption never executed | run the adoption; the shared copy already exists |
| *ABSENT* | no kit equivalent; two or more apps forked in parallel | design the shared component from the union |
| *TEMPLATE* | two or more apps instantiate the same architectural *pattern*, with no shared code and no ancestor file | extract the pattern as scaffolding — the union is already agreed, so this is the *easiest* class, not the hardest |

=TEMPLATE= was added 2026-07-29 by the census extension and is not a
refinement of =ABSENT= — it implies the opposite difficulty. =ABSENT= means two
apps solved one problem in parallel and their union must be negotiated.
=TEMPLATE= means they solved it *the same way on purpose*, from a shared
description, so the design consensus already exists. See §5c.

Direction matters more than magnitude. A *STALE* fork is safe to delete and
risky to keep; an *AHEAD* fork is the reverse. Deleting an *AHEAD* fork silently
regresses the app, and nothing in a line-count table warns you.

** Measurement caveat, stated once

Two different diff measures appear below and they answer different questions:

#+begin_src sh :results verbatim
diff -q A B                                   # identical? yes/no
diff A B          | grep -c '^[<>]'           # edit distance (order-sensitive)
diff <(sort A) <(sort B) | grep -c '^[<>]'    # set difference (order-insensitive)
#+end_src

The *sorted* form answers "is this the same code?" and is immune to reordering;
the *unsorted* form approximates patch size. A pair can show a large unsorted
delta and a small sorted one purely from moved blocks. Where both are given the
column is labelled. Neither is a review substitute — read the diff before
deleting anything.

six is a defect.

* 5. The =task-board= ORPHAN — promoted, never adopted

The only *ORPHAN* class in the census, and the most important entry because it
is a *process* failure rather than a code one.

| Component | Kit (promoted) | task-board (origin) | Differing |
|-----------+----------------+--------------------+-----------|
| =adaptive_layout= | 217 | 237 | 256 |
| =led_indicator=   | 168 |  99 | 139 |
| =resize_handle=   |  63 |  53 |  22 |

=task-board/docs/desktop-kit-gap-evaluation.org= (2026-07-04) specified a
two-part plan: *promote* these three into new =desktop_kit_layout= /
=desktop_kit_status= entrypoints as controlled widgets, and *adopt* the kit's
theme/settings/clipboard/about in return. Kit commit =af177de= (2026-07-04,
"layout+status: promote AdaptiveLayout/ResizeHandle/SpanHost/LedIndicator")
executed the promotion. The adoption never ran — that doc's Session State still
reads =[ ] Adoption worktree=.

Evidence of the direction, not merely the correlation: =task-board='s
=AdaptiveLayout= is still Riverpod-coupled (=ref.watch(localStorageProvider)=
plus four =ref.read= writes), while the kit's is the controlled refactor the
plan mandated (=required this.mode= + callbacks, no =WidgetRef=).

*The lesson, which generalises to this entire consolidation:* promotion without
a gated adoption step does not reduce duplication, it *increases* it — one
implementation became two. The copy-first invariant is only safe because it ends
in an explicit retire-the-fork step; drop that step and every tranche in
[[file:framework-subsumption-design.org]] terminates in the =task-board= state.

** Why this was missed, and what it says about the census method

Every earlier measure asked *"does the app import =desktop_kit=?"*. By that
measure textloom is the family's **best** citizen — 38 of 67 files, the highest
adoption ratio anywhere. An adoption ratio structurally cannot see a fork of the
*example* app, because =example/= is not the kit.

So: *cross-check app filenames against =example/= as a standard census step,
alongside app-vs-kit.* This finding is the reason the =example/= surface is now
part of the census rather than a footnote in the inventory.

** Consequence for =ui0=

=ui0= was designed as =example/= promoted from demo to oracle
([[file:framework-subsumption-design.org]] §2). That is now the wrong seed:
=example/= is the stale ancestor of a live app, so seeding =ui0= from it starts
3,937 lines behind the version people actually run. Three options, to be chosen
*deliberately* rather than fallen into by a tranche:

(a) *Seed =ui0= from textloom.* textloom already is "a standalone editor built on
    desktop_kit" — the oracle's job description.
(b) *Promote the shared engine into tier 1 / tier 2 and de-fork both.* Highest
    value, largest effort.
(c) *Retire =example/=* and let textloom be the oracle in place.

Recommendation: (b) for the byte-identical library files, (a) for the shell.
Tracked in =a9e4bfea=; it supersedes the seed assumption in =66e1b89b=.

** The independent finding inside it

=emacs_buffer_editor.dart= is *4,115 lines in =example/= and 5,949 in textloom* —
larger than any file in the kit itself (kit's biggest is =emacs_buffer.dart= at
2,768). A ~5k-line editor implementation living in an *example* app is
un-promoted engine code in the worst possible place: it reads as sample code and
is therefore treated as disposable, while being the largest implementation in the
family. =pages/org_editor_page.dart= (1,087 / 1,858) is the same shape.

Immediately available with no design decision: the 16 byte-identical files, ~2,900
lines. =x11_colors.dart= (542) and the =org_fold_example= pair (453) are pure
library code with no gallery-specific content and belong in tier 1 now.
