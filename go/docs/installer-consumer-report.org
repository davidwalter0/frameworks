** Item 2 — CleanMode, why the default is the right call here

The fork's subdir-only clean is *exactly* the pattern =spec.go='s own
=CleanSubdirs= doc warns about: "word-bank adopted [=CleanAppDir=] after a
layout change left stale top-level entries [...] stranded by the subtree-only
clean." voicelab' fork cleans only =bin/= and =gui/=, so any top-level file
whose *name* changes between releases (=NOTICE=, an icon, a launcher
wrapper) would survive alongside the new one indefinitely. Taking the package
default (=CleanAppDir=) closes that class of bug before it happens, at zero
behavioural cost today — the current payload's top-level file set is stable,
so a full clean and a subdir clean currently produce an identical installed
tree (verified: see §4).

** Item 3 — DesktopNaming, verified against the GTK application id

=DesktopByAppID= is not a cosmetic pick. Verified (not assumed) that this
app's GTK =APPLICATION_ID= (=ui/voicelab-ui/linux/CMakeLists.txt:10=) is
=com.davidwalter0.exampleUi= — identical to =Icon== and =StartupWMClass== in
the shipped =.desktop= template. The fork installs the entry as
=voicelab-ui.desktop=, which does *not* match the application id; per
=spec.go='s documented Wayland finding (window-icon resolution keys off the
installed =.desktop= *filename*, not its content), the fork's naming is the
exact bug word-bank already fixed elsewhere in this family. Switching to the
package default closes it here too. Confirmed empirically: the real install
in §4 produced =com.davidwalter0.exampleUi.desktop=, with =Icon== and
=StartupWMClass== inside it unchanged and already matching.

*Operational wrinkle this creates* (flagging, not fixing — outside owned
paths): a host with an *existing* install from the old fork has a stale
=voicelab-ui.desktop= in =$PREFIX/share/applications/=. This new installer's
=Uninstall= only removes =desktopTarget()= (the app-id name), so it will not
clean up that old file. A first real cutover should either =rm= the old name
once, or the parent should decide whether =pkg/installer= ought to know about
a "previous name" to clean. Recorded for the parent, not acted on here.

* 5. libdartjni.so — recorded, not implemented

voicelab' Flutter release bundle *does* ship
=lib/libdartjni.so= (128,328 bytes) — confirmed present in the real bundle
used for §4's verification, same file word-bank's
=scripts/lib-appdir.sh:92= (=rm -f "$appdir/usr/bin/lib/libdartjni.so"=)
strips before AppImage packaging.

*Whether voicelab needs the strip today: no, for a different reason than
word-bank has it.* word-bank's comment is explicit about *why* it strips:
"never loaded on Linux; phantom libjvm dep" — that dependency chase happens
inside =linuxdeploy=, which walks the AppDir's =.so= files and gets confused
by the Android-only JNI shim. voicelab does not use =linuxdeploy=/AppImage
at all — its distribution path is =pkg/installer='s tar-extract, which never
inspects =.so= dependencies. So the specific failure mode the strip exists to
avoid cannot occur on voicelab' current path.

The only cost of leaving it in is size: 128 KiB inside a 46 MiB payload
(~0.28%), negligible. If =pkg/installer= or a future AppImage path is ever
made to own stripping uniformly (as the design doc's "Honest remaining risk"
suggests it eventually should), voicelab would benefit purely on
cleanliness grounds, not correctness — recorded for that future work, not
acted on here since it would mean touching =pkg/installer=, which is
out of scope for this consumer task.

* 6. Defect found in pkg/installer — FIXED 2026-08-07

** 6.0 Resolution (read this before the original report below)

*The defect described in §6.1 is fixed, and the reason it was findable only by
a real-artifact run is fixed too.*

*The code fix.* =icons.go='s =ensureIconTheme= now writes =IconThemeMarker= on
BOTH authorship paths — the system-copy branch and the synthesized-fallback
branch — because the installer authored the file in both cases. Previously the
marker was written only after the fallback, so on any host WITH a real
=/usr/share/icons/hicolor/index.theme= (i.e. every real desktop) the copy
succeeded, no marker was written, and =Uninstall= then declined to remove a
file it had itself created. The current source carries that reasoning inline,
in past tense, at the point of the fix.

=removeWrittenIconTheme= additionally gained a =hasRemainingIcons= guard, so a
shared prefix holding another application's icons keeps its theme index even
when the marker says the file is ours.

*The test fix, which matters more.* The original report's sharpest observation
was that =installer_test.go= redirected =SystemHicolorIndexTheme= to a
deliberately-absent path in EVERY test, so the copy-success branch — the common
case — had no coverage at all and the suite could not have caught this. Four
tests now cover the four outcomes:

| test | branch |
|------+--------|
| =TestUninstallRemovesOwnIconTheme= | fallback-written index.theme is removed |
| =TestUninstallRemovesCopiedSystemIconTheme= | COPY-SUCCESS path: copied index.theme is removed |
| =TestUninstallKeepsForeignIconTheme= | a pre-existing/foreign index.theme survives |
| =TestUninstallKeepsIconThemeWhenOtherIconsRemain= | =hasRemainingIcons= guard holds |

=TestUninstallRemovesCopiedSystemIconTheme= points =SystemHicolorIndexTheme= at
a stand-in file with content DISTINCT from the fallback template, then asserts
the installed =index.theme= is that content — so if the copy branch ever stops
running, the test fails with "copy-success path did not run" rather than
passing vacuously against the fallback. That assertion is what makes it
load-bearing rather than merely present.

*Process note worth keeping.* This document said "reported, not fixed" for over
a week after the repair landed, and its Next Steps still asked the parent to
decide whether to fix it. A report that outlives its subject is not neutral —
it invites either re-doing settled work or distrusting the code. The finding
below is retained verbatim because it is *why* those three tests exist.

** 6.1 The original report (2026-07-29, retained as history)

*=Uninstall= does not remove a copied (as opposed to fallback-written)
=index.theme=, nor the resulting empty theme-directory scaffolding, when the
host already has a real system hicolor theme.*

Mechanism (read from =icons.go=, confirmed by the real run in §4):
- =ensureIconTheme= (called by =Install= via =refreshIconCache(..., true, ...)=)
  checks whether =theme/index.theme= exists; in a fresh prefix it does not, so
  it tries =CopyFile(SystemHicolorIndexTheme, dst, ...)=. On any host with a
  real =/usr/share/icons/hicolor/index.theme= (this one included — Mar 2018,
  55,507 bytes), that copy *succeeds*, and the function returns *without*
  writing =IconThemeMarker=. The marker is written *only* on the fallback
  path (system file absent → write the minimal built-in template).
- =Uninstall= → =removeWrittenIconTheme= checks *only* for =IconThemeMarker=;
  finding none, it treats the =index.theme= as "not ours to remove" and
  leaves it — along with the (now empty) =256x256/apps=, =scalable/apps=,
  =hicolor/= directories and =icon-theme.cache= — behind after uninstall.
- =installer_test.go:100-102= always redirects =SystemHicolorIndexTheme= to a
  deliberately-nonexistent path before testing =ensureIconTheme=
  /=removeWrittenIconTheme=, so the test suite only ever exercises the
  fallback+marker branch. The copy-succeeds branch — which is the *common*
  case on any real desktop Linux host — has no test coverage for its
  uninstall behaviour, and this is exactly why it took a real prefix on a
  real host to surface.

*Observed, concretely* (this run): after =Install= then =Uninstall= into a
throwaway prefix that held only this one app, =find $PREFIX= after uninstall
still listed =share/=, =bin/=, =share/applications/=, =share/icons/hicolor/=,
=hicolor/index.theme=, =hicolor/256x256/=, =hicolor/256x256/apps/=,
=hicolor/scalable/=, =hicolor/scalable/apps/= — i.e. the prefix did *not*
fully return to its prior (nonexistent) state; it returned to "empty
directory tree + one leftover =index.theme= file" rather than gone.

*Whether this is a bug or a documented tradeoff*: the code's own comment
("never touch someone else's theme index") is a *correct* policy when the
=index.theme= genuinely belongs to another application sharing the prefix.
The gap is that the ownership test (=IconThemeMarker=) can't distinguish
"someone else's theme" from "our own copy of the system theme, into a prefix
that otherwise held only this one app" — those are observationally identical
from =Uninstall='s point of view today. Reporting for the parent to decide,
per this task's instructions not to patch =pkg/installer=; three other forks
are pending migration onto it and the fix (if any) affects all of them.

* Glossary
- payload :: the gzip tar of a staged install tree, embedded via =go:embed=
  behind the =withpayload= build tag.
- =Spec= :: the per-application description (=go/pkg/installer/spec.go=) that
  turns the shared installer into one app's installer.
- app-id :: the reverse-DNS identifier (=com.davidwalter0.exampleUi=) that
  must match across the GTK application id, =.desktop= =Icon==/=StartupWMClass==,
  and the hicolor icon basename.
- =IconThemeMarker= :: the sentinel file (=.frameworks-wrote-index-theme=)
  =pkg/installer= uses to decide whether it is safe to remove =index.theme=
  on uninstall.
